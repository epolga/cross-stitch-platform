# GSC indexing investigation — August 2026

Durable record of a multi-day investigation into GSC "Duplicate without
user-selected canonical" and "Crawled – currently not indexed" issues,
plus a related detour into whether Pinterest ad spend affects organic
traffic. Written 2026-08-23 because `Focus.md` gets periodically archived
(items collapsed to one-line pointers, full narrative moved to
`docs/session-log/`) — this file is the place that keeps the full
reasoning and exact tracking-file locations regardless of what happens to
Focus.md between now and the check-in dates below.

**All open threads below share the same check-in date: ~2026-09-06.**

## 1. General noindex rule (shipped, no follow-up needed)

**Problem:** GSC kept flagging "Duplicate without user-selected
canonical" for a growing list of URL patterns, each fixed individually
and each fix missing the next case: `?photo-to-cross-stitch?catalogPatternId=`,
`/?page=59` (legacy pagination param), `/?utm_source=.../?gclid=...`
(tracking params), `/Free-India-Charts.aspx?pageSize=10&nPage=1`
(redundant defaults generated by `PaginationControl.tsx`'s "First page"
button), `/albums/9` (numeric duplicate of the pretty-slug album URL).

**Fix:** replaced every per-param enumeration with one general rule —
noindex whenever the actual request URL doesn't match its canonical (any
search param present, or for albums, access via the numeric
`/albums/[id]` route instead of the pretty slug). Implemented in:

- `web/src/app/page.tsx` (homepage)
- `web/src/app/photo-to-cross-stitch/page.tsx`
- `web/src/lib/album-metadata.ts` (new — shared by `albums/[albumId]/page.tsx`
  and `[slug]/page.tsx`, since Next's generated route types forbid extra
  named exports from a `page.tsx` file)
- `web/src/middleware.ts` (redirects legacy `/?page=N` to `/`)

**Known behavior change:** `/photo-to-cross-stitch?source=`-only (no id)
used to stay indexable deliberately; it's now noindex too, since it's not
distinct content from the bare URL.

**Not yet covered:** individual design pages (`/{Caption}-{albumId}-{page}-Free-Design.aspx`)
still set `robots: 'index, follow'` unconditionally — no canonical-vs-actual
check. Judged lower-risk to leave as-is for now (see §3's reasoning on why
orphaned URLs there don't reproduce this problem), but worth applying the
same general rule eventually for full consistency.

Deployed and verified live 2026-08-23 (`app-260823_185935847562`).
Validate Fix was clicked in GSC the same day. **Check ~2026-09-06**
whether the "Duplicate without user-selected canonical" status cleared
(Google's validation typically takes ~2 weeks), and whether anything
similar has shown up on a route type this fix didn't touch.

## 2. Pinterest ad spend vs. organic traffic ("halo effect")

Started from Olga asking about a US traffic drop around 2026-08-14, which
traces back to a GSC average-position decline first spotted 2026-08-12:
08-09 (11.0) → 08-10 (13.3) → 08-11 (16.3), a new 3+ week high, with a
sharper US-specific slice (11.9→16.5→20.1, clicks 45→29). **Ruled out on
our side before looking externally:** server 5xx rate (stayed low all
week, 0.08-0.32%), Googlebot-specific error rate (also low), response
latency (no degradation), recent deploys (none touched
redirects/canonical/sitemap/middleware), and — checked directly in the
GSC UI — Manual Actions and Security Issues (**both clean**, ruling out a
penalty/policy flag). Page-level pattern was broad/mixed, not isolated to
one template. This pointed at an external/mechanical cause rather than a
site bug, leading to the three candidates below (an initially-suspected
unconfirmed "Google dance" industry-wide volatility report from
~2026-08-01 turned out superseded by the confirmed spam update in the
confound note below — third-party trackers had called the earlier
volatility "a wobble, not a storm").

Timeline of what actually happened to the ad budget:

- ~$5/day through late July
- cut to ~$4.2-4.6/day around 2026-08-07
- raised to ~$6.5/day on 2026-08-17
- **set to $5.5/day on 2026-08-23** (current value — see also
  `automation/pinterest-agent` DAILY_BUSINESS records, `spend` field, for
  the authoritative up-to-date number if this file goes stale)

**Evidence for a real correlation** (not just the $4.5→$6.5 window, which
turned out confounded — see below): whole-history Pearson correlation
between spend and GA4 organic sessions, 97 days
(`automation/pinterest-agent/scripts/_check_halo_effect.ts`): r=0.567
same-day, r≈0.51-0.53 at 1-3 day lag. A prior natural experiment (the
2026-06-19 cut from $11.84→$4.89/day) showed organic sessions drop -26.5%
in the same direction. Cross-validated via two independent Google data
sources (GSC clicks/position vs. GA4 Organic Search sessions), both
showing the same ~30-37% lift in the $6.5-budget window vs. the
$4.5-budget window; GA4 Direct-channel sessions stayed flat, ruling out
"saw a pin, typed the URL" as the mechanism — the lift lands as organic
search specifically.

**Confound found:** a *confirmed* Google spam update ran 2026-08-18
12:30pm ET → 2026-08-21 4:50am ET, landing almost exactly on the
budget-raise date and the sharp position recovery (08-18). This makes the
short $4.5-vs-$6.5 before/after comparison unreliable on its own — can't
cleanly separate "budget raised" from "global spam update reshuffled
rankings" using that window alone. The whole-history r=0.567 correlation
predates this update and isn't affected by the confound.

**A third candidate cause, found by Olga:** `GSC_INDEX_SAMPLE` history
shows estimated indexed pages rose from ~24% (mid-July average) to ~36%
(mid-August average) — a statistically real multi-week trend (SE of the
difference ≈1.3pp, difference ≈12pp), driven by unrelated site-side
canonicalization/lastmod work, not spend. Newly-indexed pages almost
always start with weak positions, so adding ~650 of them to the indexed
pool mechanically drags the site-wide *average* position down —
potentially explains at least part of the 08-11..17 dip without any
external cause.

**Bottom line:** three non-exclusive candidate explanations (spend halo
effect, Google spam update settling, indexed-page-count growth dragging
the average). **Check ~2026-09-06**: by then the spam update's effect
should be fully settled and indexed-count growth may have plateaued — if
position stays elevated after both of those resolve, that's much cleaner
evidence for the spend/halo effect specifically.

**Direct ROI (separate from the halo-effect question):** last 21 days as
of 08-23, proportionally-attributed Pinterest-ads-only P&L was
**-₪187/21 days** (spend ₪321.79 in USD-equivalent, attributed revenue
only ₪134.46) — this is why Olga cut spend from $6.5 to $5.5 rather than
raising it further, regardless of how the halo-effect question resolves.

## 3. Backfill A/B test — does the 2026-07-09 AI text actually help indexing?

**Background:** 2026-07-09, 5261/5270 designs got AI-generated
visually-grounded title/description (Claude Haiku vision), replacing a
generic template that 65% of designs shared verbatim (Google's "scaled
content abuse" pattern). 269 designs that already had GSC traffic
pre-backfill were reverted to old text, nominally as a "control group."

**The original control was confounded:** those 269 were selected because
they *already had GSC traffic* — not randomly — so comparing their
83.6% indexed rate against a random backfilled sample's 29.3% mostly
measured "already-successful pages" vs. "the long tail," not the text's
effect. (Verified via `automation/pinterest-agent/scripts/_check_backfill_vs_control.ts`.)

**Real fix (2026-08-23):** a properly randomized test —
`automation/pinterest-agent/scripts/_setup_backfill_ab_test.ts`. Pool =
the ~5002 backfilled designs NOT in the original 269 (genuinely the
previously-unindexed long tail). Randomly split 150/150:

- **control**: reverted to pre-backfill text via each design's own
  `SeoDescriptionPrevious` backup (verified live: design 4942 "Bear" now
  serves the old generic title/description)
- **treatment**: left untouched (new AI text)

Group membership (both designId lists) saved to
`automation/pinterest-agent/reports/ab-test-backfill-groups.json` — use
that file, not a fresh random sample, when checking back.

**Check ~2026-09-06:** re-run URL Inspection on both saved groups (same
method as `_check_backfill_vs_control.ts`) and compare indexed%. If
treatment is meaningfully higher, the backfill helps; if similar, the
root problem is something else (see §5). **Afterward, revert the 150
control-group designs back to the new AI text** — they're real live
pages, not meant to stay on old text long-term — via
`backfill-visual-seo.ts --force --designIds=<the 150 from the JSON>`.

## 4. Caption-rename batch — recrawl trigger for stale, un-indexed pages

**The problem this targets:** among "Crawled – currently not indexed"
design pages, a 200-URL random sample found the *majority* pattern is
staleness, not active rejection — 95/125 not-indexed pages last crawled
30-90 days ago, 28 more 90+ days ago (some since December 2025), only
2/125 crawled in the last month. (Olga's GSC screenshots showed examples
crawled within days — that's an artifact of the UI's default sort by
most-recent-crawl-first, not representative of the 3.43K population.)

**Why not just bump lastmod again:** already tried and demonstrably
unreliable. `Owl-9-201-Free-Design.aspx`'s sitemap `<lastmod>` was bumped
2026-07-27 (a month before this was checked) but it *still* hadn't been
re-crawled since 2025-12-27 as of 2026-08-23. `Lord-Lakshmi-32-14` got
the identical 07-27 lastmod bump and *was* re-crawled recently (08-20) —
so the same signal works for some pages and not others; it's not reliable
enough alone.

**The lever used instead: change `Caption`, which changes the URL.**
`CreateDesignUrl()` (`web/src/lib/url-helper.ts`) builds the URL from
`Design.Caption`, not `SeoTitle` — and the 07-09 backfill only ever wrote
`SeoTitle`/`SeoDescription`, never `Caption`. So this lever was
genuinely untried, not a repeat of something already attempted.

**Why this doesn't recreate today's duplicate-URL problem (§1):**
design-page lookup (`web/src/app/[slug]/page.tsx`,
`parseSlugForDesign`) resolves by **albumId + page number only** — the
caption text in the URL is decorative and never checked. So:
- the old URL keeps resolving (verified: `Flowers-17-337-Free-Design.aspx`
  still returns 200 after `Design 2535`'s caption changed)
- but it becomes **orphaned** — every internal link on the site is
  generated from the live `Caption` value at request time, so nothing
  links to the old slug anymore once `Caption` changes
- this is the opposite of the earlier duplicate-URL problem, where
  variant URLs (e.g. `catalogPatternId=`) stayed indexable specifically
  *because* they kept getting fresh internal links from a live button on
  every page — canonical alone wasn't enough to override that signal.
  An orphaned URL with no internal links reinforcing it doesn't have that
  problem.
- individual design pages don't have the general noindex rule from §1
  (`robots` is always `'index, follow'`) — judged acceptable here
  specifically because of the orphaning argument above; would still be
  worth closing eventually for full consistency.

**Scope, deliberately incremental:** 150 of ~4702 eligible designs
(~3%), not a mass simultaneous rename — Olga's concern was that renaming
thousands of URLs at once could look like a suspicious traffic-pattern
spike to Google even if not technically "spam." Small batch first, scale
up gradually only if it demonstrably helps.

**How the new captions are generated:**
`automation/pinterest-agent/scripts/_rename_stale_captions.ts` — a
text-only Claude Haiku call per design (no vision needed — reuses the
already-generated `SeoTitle`/`SeoSubjectBlurb`), asking for a short
(2-4 word) distinctive caption. **First dry-run produced bad output**:
19/150 captions contained "jewel"/"jeweled" (the underlying `SeoTitle`
generator has a stylistic tendency toward "jewel-toned" as a color
descriptor), plus 2 exact-duplicate captions among the 150. Tightened the
prompt to explicitly ban generic decorative/color-mood filler words
("jewel-toned", "bold", "pastel", "vibrant", "colorful", "pixelated")
unless literally central to the design, and require naming the concrete
subject. Re-run: 5/150 flagged, 0 duplicates. The actually-executed batch
(a different random draw) came out even cleaner: 2/150 flagged
("Wolf Portrait Pixelated", "Pastel Santa Face" — arguably legitimate
descriptors, not filler, since cross-stitch patterns are literally
pixelated and "pastel" can be an accurate palette description), 0 exact
duplicates. Judged acceptable — the metric that actually matters (exact
duplicate captions, which would reproduce the original "Cushion Cover
×160" problem) is zero; word-level repeats (e.g. "Golden" ×14) are always
paired with a different concrete noun each time.

Executed and verified live 2026-08-23: design 2535's canonical is now
`Magenta-Petunias-17-337-Free-Design.aspx`; old
`Flowers-17-337-Free-Design.aspx` still 200s (orphaned, not broken).
Sitemap.xml takes up to ~1hr to reflect the new URLs (known S3 cache
TTL — see the 2026-07-09 sitemap-poisoning fix in
`docs/session-log/2026-07.md` for why that cache exists).

Batch excludes the §3 A/B test's 300 tracked designs and the original
269, so neither experiment confounds the other. Full list saved to
`automation/pinterest-agent/reports/caption-rename-batch.json`.

**Check ~2026-09-06:** did these 150 get (re)crawled faster than the
general stale population? If yes, scale up gradually to more of the
~4702-design pool (repeat `_rename_stale_captions.ts` in further batches
of similar size, excluding designIds already renamed). If no meaningful
difference, the crawl-budget-neglect theory needs rethinking — possibly
the site's overall crawl budget/authority is the real bottleneck, not
individual-URL staleness.

**Automation decision (2026-08-23, Olga asked about cron):** don't wire
this into the recurring `cross-stitch-daily-pipeline` Lambda yet — the
technique itself is unvalidated until the 09-06 check above. If it's
confirmed to help, add it as a pipeline step with guardrails: modest
batch size per run (comparable to this 150), exclude designIds already
renamed (track via a DDB marker or the accumulated report files) and
both A/B-test groups, and don't run too frequently — repeated large URL
churn is closer to the "looks spammy" risk Olga flagged before approving
the first batch, even though a one-off batch of this size wasn't.

**Correction, same day:** the original 150-design pool was filtered only
by "already backfilled, not in either A/B-test group" — NOT by actual
indexing status, despite that being the whole point of the exercise.
Olga caught this ("надеюсь, ты меняешь названия только неиндексированных
дизайнов"). Checked properly (exact URL reconstruction from each
design's real albumId+page against ~4 months of GSC Search Analytics
page-level data, not naive caption-text substring matching, which gave
false matches like "Flowers" → a completely different design's
"Forget-me-Not-Flowers" URL): **22 of the 150 had real prior search
visibility** (nonzero impressions) under their old URL — likely already
indexed or fluctuating in/out, not the neglected-long-tail case this
batch was meant to target. **Reverted those 22 back to their original
caption** same day (`_revert_flagged_caption_renames.ts`, list in
`reports/caption-rename-flagged-for-revert.json`), restarted the app
server, and confirmed both the live page *and* sitemap.xml correctly
reflect the reversion (sitemap wasn't stale this time — the earlier
"~1hr S3 cache" note above was a one-off observation, not something to
assume is always the delay; check freshly each time rather than
assuming a fixed wait). **Fixed the script for future batches**:
`_rename_stale_captions.ts` now fetches GSC Search Analytics page data
(120-day lookback) before sampling and excludes any design whose current
URL already has nonzero impressions — pool dropped from 4702 to 3999
candidates once this filter was added. This is still an imperfect proxy
(a page can be indexed with zero impressions if there's no search
demand for it) — not a substitute for checking actual GSC coverageState
via URL Inspection if a fully rigorous filter is ever needed, but a real
improvement over no filter at all. **The 150 currently live are the
post-revert set** (128 original + 0 replacements — the pool was not
topped back up to 150 after removing the 22; if hitting exactly 150
matters for a clean before/after comparison at the 09-06 check, sample
22 more from the (now GSC-visibility-filtered) pool before checking.

## 5. Thematic/genre-level content concentration may block indexing regardless of text (documented, not yet acted on)

**Status 2026-08-23: root cause narrowed down with concrete evidence.
Olga asked to document and hold — no fix decided or implemented yet.**

A minority of "Crawled – currently not indexed" pages are being
*actively* re-crawled (unlike §4's majority staleness pattern) and still
excluded despite already having good AI-generated text. Concrete
example: `Lord-Lakshmi-32-14-Free-Design.aspx` — last crawled 2026-08-20
(very recent), already has the 07-09 visually-grounded backfill text
("Jewel-Toned Lakshmi on Pink Lotus Bloom", a real photo-derived
description), still not indexed. This proves new per-page text alone
isn't sufficient for at least some pages — it's a repeated, deliberate
Google judgment, not staleness.

**Ruled out:** literal image duplication. The existing Gap-3 pipeline
(`find-duplicate-designs.ts` metadata pass +
`verify-duplicate-designs-visual.ts` SHA-256/dHash pass, run 2026-07-19/25,
59 designs across 54 groups already canonicalized via `CanonicalDesignId`
— see `docs/session-log/2026-07.md`, "SEO Gap 3") never flagged
Lord-Lakshmi at all — confirmed by grepping both
`automation/pinterest-agent/reports/duplicate-designs.json` and
`duplicate-designs-visual.json`. Its image genuinely isn't a near-duplicate
of any specific sibling.

**Real finding: thematic/genre-level concentration, not image-level
duplication.** Lord-Lakshmi belongs to Album 32 (checked via
`GET /api/albums/32?pageSize=200&nPage=1`), which has **72 designs, every
single one tagged `subject: "culture"`**, overwhelmingly Hindu/Indian
religious and cultural iconography, with the same named subjects
recurring many times as *different* (not duplicate) artworks:

- Ganesha: 6 variants (Ganesha ×4 including "Lord Ganesha", "Dansing
  Ganesha" ×2)
- Krishna: 8 variants (Krishna ×2, Baby Krishna ×2, Lord Krishna, Radha
  Krishna ×3)
- Lakshmi: 3 variants (Lakshmi ×2, Lord Lakshmi)
- Hanuman ×2, Lord Rama ×2, Muruga/Lord Muruga ×3, Indian Girl ×3, Sri
  Sarada Devi ×2, Bharatnatyam-dance-themed ×4, Indian Woman ×2, Ashram
  ×2, Woman in Saree/Blue Saree ×2

Each is a genuinely distinct piece (different pose/composition/deity),
so the existing byte/perceptual-hash tooling correctly doesn't flag
these as duplicates of each other. But the sheer concentration — a
72-design album where a handful of named subjects repeat 2-8 times each,
all under one broad theme — is structurally similar to the *original*
2026-07-09 root cause (generic, low-differentiation content at scale)
just operating at the genre/subject level instead of the literal
text/image level. This is a plausible reason Google's quality classifier
keeps excluding pages like this one even with good per-page text: the
page competes within a large internal cluster of similar-themed content,
not just against the rest of the web.

**Not yet decided:** whether/how to intervene. Open questions for when
this gets picked back up — is this legitimate diverse content that just
needs more site-wide authority/time, or does it warrant something
active (e.g. strengthening differentiation further for designs whose
named subject repeats often within an album, restructuring how such
albums present to search engines, or something else)? No existing tool
addresses genre/subject-level clustering — would need new tooling
(e.g. counting named-subject repetition per album using the existing
`SeoSubjectBlurb`/Caption data) if this direction is pursued.

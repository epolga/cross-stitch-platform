Follow-up to the 2026-07-12 finding (`docs/srs/01-SRS-Website.md` §5) that six
entities existed in code but weren't in the formal `dynamodb-schema.md`
contract: `ConverterPatterns`, `CrossStitchLikes`, `FeatureRequests`,
`CrossStitchBlogReactions`, `EditorEvents`, `SearchQueries`.

**Live-verified all six** via `aws dynamodb describe-table`/`describe-time-to-live`,
cross-checked against the EB environment's env vars for name overrides: all
six use their code-default table names live (only `DDB_SEARCH_QUERIES_TABLE`
is explicitly set, to the same value as the default — not a real override),
all `ACTIVE`, key schemas match code exactly. Added §4.9-4.14 to
`docs/integration/dynamodb-schema.md` with full attribute tables, following
the existing `PasswordResetTokens`/`SubscriptionEvents` pattern.

**Real bug found along the way:** three tables (`ConverterPatterns`,
`EditorEvents`, `SearchQueries`) write a TTL-intended epoch attribute
(`expiresAt`/`ttl`) on every item expecting DynamoDB to auto-expire old rows
— but DynamoDB TTL was **DISABLED** on all three live tables. `EditorEvents`
was the most consequential (8,221 items and growing, 90-day TTL intended,
never applied); `SearchQueries` similarly (2,084 items). `ConverterPatterns`
(23 items) has a second, independent gap: even where the code *tries* to
enable TTL (only on first-ever table creation), no code path ever writes the
`expiresAt` attribute at all.

**Fixed 2026-07-25** for `EditorEvents`/`SearchQueries` — a one-off
`aws dynamodb update-time-to-live --table-name <T> --time-to-live-specification
"Enabled=true,AttributeName=ttl"` per table (infra-only, no code change
needed), confirmed `TimeToLiveStatus: ENABLED` on both immediately after.
DynamoDB's TTL sweep isn't instant (expired items typically clear within
~48h of the item's `ttl` timestamp passing) — no need to check back sooner.
`ConverterPatterns` is **not fixed** — needs a code change (write
`expiresAt` in `savePattern`/`updatePattern`) before the infra toggle would
do anything; deferred as low-priority (only 23 items).

## ConverterPatterns createdAt/modifiedAt split — built, tested, deployed (2026-07-25)

Found while investigating the DynamoDB audit above: `createdAt` was
misleading — `updatePattern()` used to overwrite it on every resave (a full
`PutItemCommand`), so the "Open" saved-patterns list's sort-by-`createdAt`
was really "last modified," not true creation date, matching what users
already expected under the wrong field name.

**Fix:** `updatePattern()` (`web/src/lib/pattern-storage.ts`) now does a
partial `UpdateItemCommand` that never mentions `createdAt`, plus a new
`modifiedAt` field that *does* update on every save and is what
`listPatternsByOwner`'s sort and the UI (`OpenPatternDialog.tsx`,
`ProfilePatternsPageClient.tsx`) actually use. Pre-fix rows fall back to
`createdAt` for `modifiedAt` until their next resave. Vitest (10/10 files,
61/61 tests) and full `npm run build` clean. **Deployed** via
`eb deploy cross-stitch-com-env-clone` — Health Green, live-checked (`/` and
`/api/health` both 200). Committed as `72d72a5`.

Note: `ConverterPatterns`' separate `expiresAt`/TTL gap (see the audit above)
was deliberately *not* touched in this fix — different problem, still open.

## SEO Gap 3 — canonicalize near-duplicate designs — built, applied, deployed (2026-07-25)

Full arc of `docs/Focus.md` Pending #13's Gap 3, from mechanism design
through two rounds of real production canonicalization and a related
content fix. Ties to the previously-deferred near-duplicate-design-images
issue (e.g. the two near-identical Tiger designs 5421/5422, memory:
[[project_near_duplicate_design_images]]).

**Mechanism:** new `CanonicalDesignId` (N, optional) attribute on the DESIGN
row (`web/src/app/types/design.ts`, read in `web/src/lib/data-access.ts`'s
cache-load mapping). `web/src/app/designs/[designId]/page.tsx`'s
`generateMetadata` looks it up: if set, fetches the target design via
`getDesignById` and points `alternates.canonical`/`openGraph.url` at *that*
design's URL instead of its own — `robots` stays `index, follow` (standard
canonical practice, not deindexing). The page's own Pinterest-share/JSON-LD
logic still references its own image/URL, unaffected. Vitest (61/61) and
full `npm run build` both clean. Committed as `12b0b91`.

**Duplicate detection, two passes (the first alone wasn't trustworthy
enough to act on):**
1. `find-duplicate-designs.ts` (built 2026-07-19, run then, not previously
   surfaced in Focus.md) — metadata-candidate pass, groups by (Caption,
   AlbumID, Width, Height, NColors). Found 101 candidate groups / 219
   designs. Documented in its own header as producing false positives.
2. `verify-duplicate-designs-visual.ts` (built 2026-07-25) — computes
   SHA-256 of each design's actual photo (byte-identical = zero-false-
   positive-risk "confirmed-duplicate") plus a dHash perceptual-hash
   Hamming distance (weaker signal, "worth-a-look" only, never auto-
   applied). **Concretely confirmed false positive:** the "99 Names of
   Allah" group (8 designs, same border/font/layout template) — visually
   inspected two of its images directly and confirmed they list *different*
   Arabic names, a real series, not a duplicate — despite dHash landing in
   the same distance range as true duplicates. This is why dHash alone was
   deliberately never treated as sufficient to act on.

**Round 1 — byte-identical pass:** of the 101 candidate groups, 39 groups
(43 designs) were byte-identical confirmed duplicates, applied via
`apply-confirmed-canonicals.ts --apply` (union-find clustering, lowest
DesignID per cluster = canonical). Spot-checked two pairs directly
("Cushion Cover" 3495/3537, "Brittany Spaniel" 1810/1822) — both literal
same-file duplicates (matching MD5).

**Round 2 — manual visual pass:** Olga reviewed the remaining 22
"worth-a-look" groups design-by-design (real images, not just dHash
numbers) — 15 more groups (16 designs) confirmed as genuine duplicates
(same photo, different crop/compression, not byte-identical but visually
identical): Peacock ×2 pairs, Soccer Ball, Pumpkin, Hummingbird, Pigeon,
Tulips, Lady, Mushrooms, Owl, Conwy Castle, Lips, Butterfly, Horse, Pelican,
Butterflies. Applied via `set-canonical-design.ts`.

**Total: 59 designs across 54 groups canonicalized.**

**Explicitly deferred, not touched — distinct cases for a separate decision,
not "we'll get to it":**
- "99 Names of Allah" (8 designs), "Cushion Cover" ×2 pairs (3312/3519 —

### Template-series case (99 Names of Allah) — fixed via backfill-visual-seo.ts visibleText field

Real root cause: `backfill-visual-seo.ts`'s vision prompt never asked the
model to read the actual Arabic text in the image, so all 8 designs got
generic, near-identical descriptions ("green Arabic calligraphy...") despite
each stitching completely different names — *that's* the genuine reason
they looked like duplicates to Google, not the image composition.

**Fix:** added a `visibleText` field to the structured-output JSON schema,
plus prompt instructions to transcribe any readable lettering (original
script + transliteration + translation) and make it the primary
differentiator in the title/body when present. Code-level fallback: if the
model's prose doesn't already include the transcribed text verbatim, append
it as a plain sentence — same "don't fully trust the model to follow
free-form instructions" lesson as the script's existing paragraph-count
enforcement. Dry-run tested on 2 designs first (confirmed each now lists
its own distinct set of names, Arabic + transliteration + English), then
applied for real to all 8
(`--designIds=3351,3354,3357,3360,3363,3366,3369,3375 --force`).

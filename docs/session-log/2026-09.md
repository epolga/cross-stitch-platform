### Photo-converter CPU saturation — closed

Full write-up: `docs/web/photo-converter-cpu-saturation-2026-09.md`.
Root cause (found 2026-09-01): `/api/convert`/`/api/convert/pdf` ran
pattern generation as synchronous JS in the request handler, blocking the
whole single `next start` process (including its own ALB/EB health check)
under any concurrent-conversion burst — caused a real ~60% GA4 session
drop, uniform across every channel, on 2026-08-31. Fixed and deployed:
Option 1 (worker threads, commit `31670f4`) moves
`convertImage()`/`buildPatternPdf()` into a Piscina worker pool; Option 5
(CPU-based Auto Scaling, `8ef2099`/`c0a66d1`, `Statistic=Maximum`/
`Threshold=65` — `Average` was tried first and found to dilute a single
saturated instance across the ASG, undetected) is a sustained-load
backstop. Both confirmed live in production 2026-09-03. Remaining Options
2-4 (concurrency limit, algorithmic cost reduction, background queue) are
optional hardening, not implemented, not required.

### Pattern-save DynamoDB item-size bug — thumbnail moved to S3

Full write-up: `docs/web/pattern-save-item-size-bug-2026-08.md`. Found
2026-08-12: `savePattern()`/`updatePattern()` guarded only the *grid*
field size, never `thumbnail` (routinely 90%+ of item size) or the total
item — a detailed/colorful pattern could fail to save with a raw DynamoDB
`ValidationException`, hitting real users through the live editor, not
just scripts. Fixed by moving `thumbnail` to S3
(`photos/converter-patterns/<patternId>.<ext>`, reusing the already-
whitelisted CloudFront `/photos/**` path — no new infra needed), in the
sequence Olga specified (backward-compatible reads before the write path,
so a pattern saved in the new format is never unreadable):

- Step 0: `resolveThumbnailSrc()` (new `pattern-thumbnail-url.ts`) reads
  both formats, wired into `ProfilePatternsPageClient.tsx` and
  `OpenPatternDialog.tsx`.
- Step 1: `storeThumbnail()` in `pattern-storage.ts` uploads on save,
  stores only the key. Real subtlety found: `updatePattern()` now
  distinguishes "no thumbnail sent" (explicit clear) from "one was sent
  but the S3 upload failed" (leaves the field untouched) — the original
  two-way logic would have wiped a working thumbnail on a transient S3
  hiccup.
- Steps 2-3 folded into step 0 — no server-side URL construction or
  `next.config.js` change needed after all.
- Step 4: one-off `backfill-thumbnails-to-s3.ts` (deleted after use, kept
  `storeThumbnail()` unexported again) migrated all 113 legacy rows,
  0 failures, spot-checked 10 across the full size range live via
  CloudFront.
- Step 5: `deletePattern()` also deletes the thumbnail from S3, no
  reference-count needed (not content-addressed, unlike sourceImageKey).
- Step 6: the now-dead legacy-format read branch removed from
  `resolveThumbnailSrc()`.

104 tests passing (added S3-mock coverage for all the new upload/delete
paths), deployed and verified live same day.

### Source-image key sharing, S3 orphans, and an ownerless-pattern auth gap

Full write-up: `docs/web/source-image-key-sharing-and-orphans-2026-09.md`.
Found while investigating whether `thumbnail` could move to S3 the same
way `sourceImageKey`/`researchImageKey` already did. Three findings, four
fix tracks, one gap deliberately left open:

- **`newPattern()` didn't reset `sourceImageKey`/`researchImageKey`/
  `sourceImageMaskKey`** — added ~6 weeks after `newPattern()` was
  written, never wired into its reset list. Fixed, committed, deployed.
  Verified live in a real browser (imported sample photo → generated →
  New Pattern → reopened import dialog → empty state, not the stale
  photo).
- **~506 MiB of orphaned S3 objects** (783/827, 94.7%, in
  `pattern-source-images/`+`research-uploads/`) — mostly from converter
  sessions that were tried but never saved, not from deletions. Bucket
  already has versioning + a 90-day noncurrent-version lifecycle rule, so
  cleanup is recoverable.
  - **Track A (delete-time cleanup)**: `deletePattern()` now deletes
    `thumbnail`/`sourceImageKey`/`researchImageKey`/`sourceImageMaskKey`
    from S3 unconditionally alongside the pattern, best-effort per key.
    A reference-counted check (these three are content-addressed, could
    in principle be shared) was the original plan but was dropped after
    checking the real data: 0 of 44 currently-referenced keys collide
    across any of the 127 real patterns — the sharing mechanism is real
    but has never actually happened, and a false-positive delete only
    degrades "Redo from Photo" on the other pattern, not a data loss.
  - **Track B (clear the existing backlog)**: originally planned as a
    blind S3 lifecycle rule by object age — corrected before implementing
    (Olga caught it): these keys are content-addressed and never
    rewritten, so a genuinely old-but-still-referenced object has the
    same `LastModified` as real garbage; age alone can't tell them apart.
    Implemented instead as a real cross-reference: new
    `web/scripts/cleanup-orphaned-source-images.ts` (kept as a reusable
    script — new orphans keep accumulating from ordinary unsaved
    converter use, unlike the one-off thumbnail backfill) fetches the
    actual referenced-key set from `ConverterPatterns`, lists all S3
    objects in both prefixes, deletes whatever isn't referenced *and* is
    older than a 48h grace period (protects an in-progress session). Ran
    for real: 697/697 deleted, 0 failures, ~457 MiB cleared. Verified a
    real referenced key from 2026-08-14 (well past the grace period)
    survived intact.
  - **Track C (migrate `thumbnail`)**: see above, done as part of Open
    item #25.
  - **Track D (the actual structural fix, requested after Olga asked "what
    guarantees new orphans stop appearing?")**: moved the S3 upload itself
    out of `api/convert/route.ts` (fired on every conversion attempt) into
    a new `api/converter/upload-source-photo/route.ts`, called only from
    `ConvertClient.tsx`'s `handleSavePattern()`. Confirmed in code first
    that this was safe: the original file lives in browser memory for the
    whole editing session (`ImportFromPhotoDialog`'s `selectedFile` ref),
    and the S3 copy is only ever read back for "Redo from Photo" after a
    reload/reopen of an *already-saved* pattern — an unsaved conversion
    never needs it. Found and fixed a real regression while implementing:
    `handleImport()` used to set `sourceImageKey`/`researchImageKey`
    straight from the convert response; since that response no longer
    carries them, this would have wiped a previously-saved pattern's
    still-valid key back to `undefined` on every Redo — removed, the save
    flow is now the only place these update. Verified live: `/api/convert`
    no longer returns the keys; converting the sample photo without saving
    left the S3 object count unchanged (139 → 139); the new endpoint
    uploads correctly when called directly.
  - Split into two commits per Olga's ask despite the interleaved diffs
    in the same files (`4e93273` memory-cleanup-only, `4f8da9e` the S3
    deferral) — reverted-then-reapplied the S3-specific hunks around the
    memory-cleanup commit to get a clean split, verified each commit is
    self-consistent in isolation.
- **Ownerless-pattern auth gap**: `GET`/`PUT`/`DELETE`
  (`api/converter/patterns/[id]/route.ts`) and `source-image/route.ts`
  only check ownership `if (pattern.ownerID)` — a row with no owner has no
  check at all. Verified dormant (the 14 ownerless rows all predate the
  `sourceImageKey` field; `POST` always requires a session and sets
  `ownerID`, so no new ownerless row can appear). **Deliberately deferred,
  not fixed** — Olga's explicit "запиши на будущее" — still listed as an
  open item in `Focus.md`.

A separate memory-cleanup fix landed alongside this investigation:
`ImportFromPhotoDialog` is always mounted (its `open` prop just toggles
visibility), so its `selectedFile`/`previewUrl` outlived the design they
belonged to after "New Pattern" — added a `resetSignal` prop the dialog
watches via `useEffect` to force-clear itself, bumped by `newPattern()`.

### AWS WAF Bot Control — reviewed 22 days of real data, shipped a targeted rule instead of a category flip

Enabled 2026-08-13 in selective-enforcement mode (CategorySeo/Advertising/
ScrapingFramework kept at native Block, everything else forced to Count).
2026-09-03: reviewed real data before deciding whether to flip any more
categories to Block. Found a real CloudWatch quirk first: only sub-rules
listed in `RuleActionOverrides` get their own per-rule metric — the 3
kept-native-Block categories have no separate metric, only the aggregate
`BotControlCommonCount` (confirmed via a live 3h `get-sampled-requests`
sample that CategorySeo/CategoryAdvertising are genuinely firing).

Pulled real 22-day totals for every Count-mode sub-rule:
`SignalNonBrowserUserAgent` dominates (546,521, ~24.8K/day) and real UA
samples confirmed it's genuinely mixed — Googlebot, Bingbot, ClaudeBot,
and Facebook's link-preview crawler sit in the *same* bucket as commercial
SEO tools like AhrefsBot and Sogou. Can't be blocked wholesale without
also cutting off wanted crawlers. `CategoryAI` (122,151) and
`CategorySocialMedia` (6,637) confirmed still legitimate. Everything else
low-volume.

Decided against any category-level flip. Shipped instead: a narrow
`BlockSeoCrawlerUserAgents` rule (priority 4, `CrossStitchBotProtection`)
— a `User-Agent` byte-match (`CONTAINS`, case-insensitive, base64-encoded
search strings — the AWS CLI requires this when the statement is loaded
from a JSON file rather than shorthand) for "ahrefsbot" or "sogou",
`Action: Block` — targets exactly the two named commercial crawlers found
sitting inside the otherwise-unblockable bucket, without touching the
category. Verified live: normal browser UA still 200, AhrefsBot UA 403.
This is the answer for any other specifically-named unwanted crawler found
later too — a narrow rule, not a category flip.

### Design-vote up/down: "clears, not switches" confirmed as intended
